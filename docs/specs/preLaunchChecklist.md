## 2. Parked review findings

Findings deferred during implementation review, not fixed before merge.

- [ ] `README.md` was fully replaced with the default `create-next-app` template during Task 1 scaffold (expected for a fresh scaffold; revisit with real project description before launch)
- [ ] `app/layout.tsx` destructures only `children` from a props type that also declares `params` (unused) — valid TS, minor consistency nit, low priority
- [ ] **Known limitation, not fixed:** `lib/supabase/middleware.ts`'s `updateSession()` (the official `@supabase/ssr` reference pattern, not custom code) has a refresh-token race condition. When multiple concurrent requests hit middleware with the same expired-but-not-yet-refreshed session cookie (a single page load fires several requests — navigation + parallel RSC/data fetches), each independently attempts to refresh; the first succeeds and rotates the refresh token, and any other concurrent request using the now-stale token gets `AuthApiError: Invalid Refresh Token: Already Used`. Supabase treats reuse as a possible theft signal and revokes the whole session, not just that one request — so the user gets fully logged out instead of the page just reloading once more. Reproduced and confirmed locally during Task 11 verification (with JWT expiry deliberately lowered to 60s to speed up testing); root cause traced to `refresh_token_already_used` in the auth error code (see commit history around this checklist entry's date for the diagnostic session). This is a documented, still-open issue upstream (Supabase GitHub issues #18981, #30241; auth-js #454) with no official first-party fix — workarounds (moving refresh off middleware, client-side `onAuthStateChange` + `router.refresh()` listeners, custom request mutexing) are all non-trivial architecture changes, judged disproportionate to this chunk's scope. **Real-world severity is much lower than what was reproduced**, since the default JWT expiry (3600s) makes the concurrent-requests-in-the-same-few-hundred-ms-window scenario rare rather than routine. Revisit if this actually surfaces in production usage, or as part of a future auth-hardening chunk.

## 3. Process/tooling gaps

- [x] Next.js 16 deprecated the `middleware.ts` file convention in favor of `proxy.ts` (function renamed `middleware` → `proxy`, same behavior/matcher config). The plan's file structure and Task 6/9/11 steps still reference `middleware.ts` by name — mentally substitute `proxy.ts`. Migrated during Task 6 (commit `4f6effb`); no outstanding action, just a naming mismatch between the plan doc and the actual repo going forward.
- [x] The root repo checkout (`chartboard/docs/impl-plans/...`) and this worktree (`chartboard/.claude/worktrees/auth-access-foundation/docs/impl-plans/...`) hold two divergent copies of the same-named plan file — the worktree's copy has a later amendment (commit `2149d68`, unit-testing `isProtectedPath`) that the root checkout never received, since it stayed on an earlier point of `development`. Early in this session the plan was read from the root checkout by mistake, causing Task 6 to initially skip the `isProtectedPath`/Vitest requirement — caught and fixed in commit `b56f616`. Going forward: always read plan files from the active worktree, never the root repo checkout, when a worktree is in use.
- [x] Tables created via raw SQL in the Supabase SQL Editor (as `supabase/migrations/0001_profiles.sql` does) do **not** automatically get the `authenticated`/`anon` role grants that the Studio Table Editor UI applies automatically when you create a table by hand. RLS policies alone are not sufficient — Postgres checks table-level `GRANT`s before RLS is ever evaluated, so without an explicit `grant select, update on public.profiles to authenticated;`, every query failed with `permission denied for table profiles` (error 42501), masked in the app as `Role: unknown` because the query's `error` was discarded (only `data` was checked). Found during Task 11 verification (dashboard showed `Role: unknown` despite `profiles.role = 'admin'` being correct in the DB); fixed by adding the `grant` statement directly into `0001_profiles.sql` (commit `7341700`) and running it manually against the already-provisioned dev/UAT project. **Action for prod:** re-running `0001_profiles.sql` in full against the prod project (already listed above) will include this grant automatically — no separate step needed, but worth double-checking after that migration run that `/dashboard` actually shows the correct role, not just that the SQL ran without error.
